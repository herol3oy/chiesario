# AGENTS.md

## Project Overview

This repository builds a provenance-first directory of historic churches in Italy.

The current reference implementation covers **Tuscany**.

The system combines:

* Wikidata
* OpenStreetMap
* Wikimedia Commons
* manually reviewed editorial overrides

The project is designed to automate repeatable data decisions while preserving source evidence and requiring human review for genuine ambiguity.

---

# Core Rule

## Never edit generated data directly

Do not manually modify files under:

```text
data/processed/
data/catalog/
web/public/data/
```

In particular, never fix data directly in:

```text
data/catalog/churches.json
data/catalog/churches_ready.json
data/catalog/churches.geojson
web/public/data/churches.geojson
```

These are generated build artifacts.

If generated output is wrong, fix either:

1. the appropriate pipeline script, or
2. `data/reviews/overrides.json`

Then regenerate the downstream artifacts.

# Source of Truth

Different kinds of information have different sources of truth.

## Raw source data

```text
data/raw/
```

Contains fetched source material and caches.

Do not manually rewrite fetched source data to correct publication results.

---

## Derived pipeline data

```text
data/processed/
```

Generated by pipeline stages.

Do not treat processed JSON as an editorial source of truth.

---

## Human editorial decisions

```text
data/reviews/overrides.json
```

This is the source of truth for manually verified exceptions and editorial decisions.

Examples:

* canonical date
* canonical coordinates
* directory type
* manual hero image
* confirmed absence of a suitable hero image
* duplicate decisions
* exclusions
* naming corrections

---

## Publication data

```text
data/catalog/
```

Generated from reviewed pipeline data.

Do not edit manually.

# QA Requirement

`qa.py` is a publication gate.

Run:

```bash
uv run qa.py
```

before generating or publishing updated GeoJSON.

The command must exit successfully.

A catalog record with:

```text
status = review
```

is considered unresolved and must block publication.

Do not bypass QA merely to obtain a successful build.

If QA fails:

1. inspect the listed QIDs,
2. determine the real cause,
3. fix the algorithm or add a justified override,
4. rebuild,
5. run QA again.

# Data Philosophy

## Preserve uncertainty

Never invent precision that the source does not support.

Examples:

If a source says:

```text
15th century
```

do not convert it to:

```text
1401
```

If a source says:

```text
circa 1420
```

do not silently convert it to an exact:

```text
1420
```

Prefer an unresolved record over an incorrectly resolved record.

---

## Preserve competing source claims

Wikidata may contain multiple:

* inception dates
* coordinates
* entity types
* images

Do not discard competing claims early in the pipeline.

Resolvers should determine canonical publication values separately from raw source preservation.

---

## Human decisions must be explicit

Do not silently hard-code one-record exceptions into generic resolver logic.

If a decision applies only to one entity, prefer:

```text
data/reviews/overrides.json
```

If the same problem occurs systematically across many entities, fix the relevant algorithm.

---

# Date Policy

Canonical dates should represent, as closely as the evidence permits:

> the origin, foundation, or construction of the church/building itself.

Do not automatically use dates referring only to:

* façades
* fresco campaigns
* restorations
* museum openings
* modern organizations
* later decorative work

Supported canonical concepts currently include:

```text
year
circa_year
decade
century
```

When manually researching a date, preserve provenance where available:

```text
source_name
source_url
note
```

---

# Coordinate Policy

Canonical coordinates should represent the actual church/building location.

Current automatic preference is broadly:

```text
Wikidata
↓
exact OSM match when Wikidata is missing
↓
manual review when necessary
```

When Wikidata and OSM substantially disagree, do not choose solely by numeric proximity.

Inspect what each point represents.

A manually verified coordinate belongs in:

```text
data/reviews/overrides.json
```

---

# Directory Type Policy

Current publication types:

```text
church
cathedral
basilica
former_church
```

Current out-of-scope types:

```text
chapel
oratory
baptistery
sacristy
abbey
monastery
other
```

Prefer the most specific meaningful physical/ecclesiastical building type.

Examples:

```text
cathedral > generic church
basilica > generic church
baptistery > generic church
sacristy > chapel/church ancestry
```

Do not change scope policy incidentally while fixing an individual record.

---

# Hero Image Policy

Hero images come primarily from Wikidata `P18` images enriched through Wikimedia Commons.

A valid licensed `P18` image is normally considered a strong candidate.

Automatic selection should reject images clearly representing:

* interiors
* paintings
* altarpieces
* portraits
* floor plans
* maps
* drawings
* frescoes
* sculptures
* statues

The desired hero is normally a useful representation of the physical building.

Manual image decisions use:

```json
{
  "hero_image_filename": "Exact Commons filename.jpg"
}
```

When an entity has been reviewed and no suitable hero exists:

```json
{
  "no_hero_image": true
}
```

`hero_image = null` is therefore a valid final state.

Do not force an unsuitable image merely to increase image coverage.

---

# Commons Licensing

Do not bypass Commons licensing checks.

Automatic hero selection currently accepts explicitly approved free-license categories.

If license metadata is uncertain or unsupported, keep the image under review rather than assuming permission.

---

# Duplicate Policy

Duplicate detection proposes candidates but does not automatically merge entities.

Human-reviewed duplicate decisions belong in:

```text
data/reviews/overrides.json
```

Expected pair format:

```json
{
  "qid_1": "Q...",
  "qid_2": "Q...",
  "status": "same_entity",
  "canonical_qid": "Q..."
}
```

When records represent the same entity:

* preserve both source entities,
* select one canonical QID,
* suppress the non-canonical publication record,
* do not delete the source research record.

---

# Override Rules

Before adding a new override:

1. identify the stable Wikidata QID,
2. determine whether the problem is systematic or entity-specific,
3. fix the algorithm if systematic,
4. use an override if genuinely entity-specific,
5. record a concise reason.

Avoid duplicate JSON keys in `overrides.json`.

If a QID already has an override, merge new fields into the existing object.

For example, do not create two separate `Q578805` keys.

Use:

```json
"Q578805": {
  "directory_type": "sacristy",
  "no_hero_image": true,
  "note": "..."
}
```

# Scaling to New Regions

Prefer generic improvements over region-specific hacks.

The intended workflow is:

```text
discover region
    ↓
run pipeline
    ↓
inspect QA/review output
    ↓
identify systematic issues
    ↓
improve generic resolver
    ↓
rerun
    ↓
manually review genuine exceptions
    ↓
QA reaches zero
    ↓
publish
```

Do not optimize for zero manual intervention.

Optimize for:

* reproducibility
* provenance
* conservative automation
* small and explicit human-review sets

# Coding Guidance

When modifying pipeline code:

* keep stages deterministic where practical,
* preserve existing source/provenance fields,
* avoid destructive normalization,
* favor explicit fields over implicit behavior,
* fail loudly on invalid manual overrides,
* keep caches reusable,
* avoid unnecessary network calls,
* do not silently ignore malformed overrides,
* keep report files useful for human inspection.

When adding new behavior, consider whether it needs:

1. a processed-data field,
2. a report field,
3. an override mechanism,
4. QA validation,
5. README/AGENTS documentation.

# Before Finishing a Change

For pipeline changes, verify the relevant downstream stages.

At minimum:

```bash
uv run apply_overrides.py
uv run build_catalog.py
uv run qa.py
```

When GeoJSON output is affected:

```bash
uv run build_geojson.py
```

When publication data is updated:

```bash
cp data/catalog/churches.geojson \
  web/public/data/churches.geojson
```

Confirm:

```text
Remaining review records: 0
```

before considering the publication build complete.

---

# Do Not

Do not:

* manually edit generated GeoJSON,
* manually edit processed JSON to fix a record,
* discard conflicting source claims during normalization,
* guess missing historical facts,
* invent exact dates from approximate dates,
* select interior/artwork images merely to avoid a missing hero,
* automatically merge duplicate candidates,
* bypass `qa.py`,
* duplicate QID keys inside `overrides.json`,
* add one-off hacks to generic algorithms when an override is appropriate.

---

# Guiding Principle

When uncertain, preserve the evidence and make the uncertainty visible.

A correct unresolved record is preferable to a confidently wrong published record.
